# 実行・デバッグと受入

## 最初に再現できる環境を用意する

- 確認日・参照URL・採用版を開発手順に記録し、`.godot-version`、CI、export templates、実バイナリの `--version` を揃える。同じ検証作業の途中で版を変えない。次のskill実行時には再確認する。
- 既存プロジェクトが古い版なら、差分を保全して最新安定版への移行内容を確認し、インポート・起動・主要回帰・書き出しを検証する。最新版で動かせない場合はエラーと阻害内容を返し、古い版への切替で済ませない。
- 開発手順に初回インポート、起動シーン、必要アセット、テスト、書き出しコマンドを置く。文書にあるコマンドが実際の構成と一致するか確認する。
- 通常プレイ、プレイテスト、破壊的な保存テストの保存先を分離する。状態プリセットはテスト用と明示する。
- 起動失敗や取得失敗はエラーと不足物を記録する。別版での自動変換や、未取得アセットの仮置換で受入成功にしない。

## 検証層を選ぶ

| 層 | 確認できること | この層だけでは確認できないこと |
|---|---|---|
| 文書lint | 必須項目、ID、共通表と個別記述の契約 | 実装や操作の成功 |
| 型・構文・format・lint | コードの読込可能性、規約 | 実データや入力の正しさ |
| 単体テスト | 計算、条件、境界値、状態の往復 | シーンの接続、描画、初見理解 |
| コンテンツ・統合テスト | 実データの参照、遷移、保存、イベント順序 | UIが押せるか、見えるか |
| 実描画と製品入力のプレイ | 見た目、衝突、操作、フォーカス、実経路 | 全分岐、他機器、初見の理解 |
| 初見観察 | 目的・操作の発見、迷い、判断材料、面白さ | 全内部状態や全異常経路 |
| 配布ビルド | 同梱漏れ、環境差、製品での起動と操作 | 未確認機器や全品質設定 |

現段階で存在する機能・データに対応するテストを使う。後半コンテンツが必要なテストを、仮実装で成功させて前段階の完了証拠にしない。文書だけの変更で全エンジンテストを毎回要求しない。

文書lintは機械的な契約に絞る。ID重複、未定義参照、必須欄、共通値との一致などを対象とし、エラー・警告・未決情報を区別する。ランタイムと制作ツールの検査規則は可能なら共用し、二重の正本を作らない。

## 実プレイの再現台本

開始状態→入力→期待状態を記述し、製品の起動経路から実行する。代表区間にはタイトル→新規開始と保存→終了→Continueを含める。長いゲームでは途中開始も使うが、全体の通過とは区別する。

- 操作は製品と同じInput MapやUIクリック経路を使う。要素IDを対象の発見に使っても、成功フラグを直接立てて操作を省略しない。
- 内部状態は読み取りとassertに使う。状態注入は前提の準備として明示し、その準備を通常プレイで達成したとは報告しない。
- 長い固定待ちより状態条件とタイムアウトを使う。描画・物理反映が必要なら同期点を設ける。
- 失敗した時点で画面、UIツリー、期待値と実値、ログを保存し、その経路を失敗として止める。後続が通ったことだけで操作失敗を無視しない。
- 主経路のほか、変更に関係する順序違い、再操作、取消、ポーズ、フォーカス、境界状態、ロードを追加する。
- 答えを知る台本の通過と、初見プレイヤーが理解できることは別に確認する。初見観察をしていない場合は未確認と書く。

Godotでは、Input Mapイベントを流すプレイドライバーと、Viewport画像・UIツリー・状態assertを組み合わせて再現する。テスト起動用の `tools/run_tests.sh` や台本用の `tools/playtest/steps/` は配置例。既存の同等機能を使うか必要な範囲を実装し、存在しないコマンドを実行済みとして扱わない。

## デバッグの一巡

1. 最小の再現条件と期待値を記録する。正常系との違いを特定する。
2. 画面、実行状態、参照先、ログの順に事実を照合する。例えば「定義を直しても画面が変わらない」なら、本編が別の埋め込み定義を読んでいないか調べる。
3. コード、生成元、配置など本来の編集元を修正する。テスト台本や表示だけで不正な進行状態を隠さない。
4. 必要な回帰テストでは修正前の失敗を確認し、修正後に同じ再現経路を通す。
5. 影響する隣接経路だけ追加で確認する。新しい変更・失敗・不確実性がなければ同じ全件テストを繰り返さない。

3D素材を入れ替えたら、見た目に加えて入場地点と衝突、操作判定の遮蔽、撮影・手がかりの画角、軸と座標を確認する。保存やイベントの修正なら、開始処理の二重発火、同フレームの順序、途中中断後の復旧を確認する。OS・フレームレート差で結果が変わる箇所は同期や条件を検査する。

## 制作ツールの実操作

[制作者向け管理画面](authoring-ui.md) のシナリオ・配置・会話・フラグを組み合わせた新規場面を、コードやデータファイルを直接編集せず作成する。操作方法は画面と利用マニュアルだけで辿れるか確認する。

新規データで作成・編集・Undo/Redo・保存・キャッシュに頼らない再読込・本編への登録・実行まで試す。既存データについても無変更往復、複数行、空文字、不正入力時の無変更を必要に応じて確認する。

エディター内での利用とツール単独起動は別の環境。単独起動の成功から、プラグイン統合、標準保存、エディターのUndo、実画面サイズを検証済みとしない。

## 画面デザインの受入

[画像生成から画面実装へ](screen-design.md) で保存した採用デザインと、同じ表示サイズ・状態のGodot実画面を比較する。配置・余白・文字・色・部品を確認し、見た目の一致と入力・編集・保存の動作を別々に検証する。生成デザインを実装スクリーンショットと取り違えない。

## QA記録テンプレート

```markdown
# QA: 対象体験 / 日付
対象リビジョン・最終修正との差分:
環境: OS / エンジン版 / 描画方式 / 機器 / 入力
方法: 単体 / 実描画 / 入力台本 / 手動 / 配布物
初期状態・保存先の分離・準備に用いた直接操作:
| 経路・操作 | 期待値 | 実際の結果 | 証拠 | 状態 |
発見した問題と修正:
修正後に再実行した範囲:
未確認の分岐・機器・品質設定・初見理解:
```

状態は成功・失敗・未実行・環境阻害を区別する。証拠にはスクリーンショット、ログ、UIツリー、状態、テスト結果を目的に合わせて使う。主要な証拠はレビュー可能な場所に保存し、巨大な生ログや再生成物の保存期間・非追跡方針を決める。

CIでは文書lint、コード検査、現段階の自動テストを必要に応じて動かす。原稿を不用意にインポートしない。LFSの必要範囲、キャッシュキー、成果物容量を考慮する。配布を求められたらCIの成功に加え、実際の書き出しと配布物での起動を確認する。
