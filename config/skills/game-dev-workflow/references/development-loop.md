# アイデアから実装まで

## 1. 体験の仮説を短く書く

最初にコンセプトとして以下を整理する。世界設定や機能一覧だけで開始しない。

- 誰が、どのような場面で、何をして楽しむゲームか。
- プレイヤーが繰り返す動詞と、その結果を確かめる方法。
- 一番見せたい瞬間と、緊張・発見・達成などの感情。
- 1回のループとセッションのおおよその長さ、対象機器と操作。
- MVPに含める一つの完結した体験、今回は作らないもの。
- 体験・技術・制作量のうち最も不確かな仮説と、その検証方法。

例: 「水位を操作する→足場が変わる→渡って近道を発見する」を一画面で検証する。水流シミュレーションが本当に必要かもこの段階で切り分ける。ゲーム固有の案を勝手に別ジャンルへ変えない。

## 2. 仕様を実装可能な契約にする

[文書構造](document-structure.md)のシステム・個別コンテンツのテンプレートを使う。実装直前の機能について、入力、状態、数式、優先順位、副作用、保存、画面への反応が一意に読めるか確認する。

仕様作成時に [制作者向け管理画面](authoring-ui.md) の編集項目、画面遷移、データ契約、制作経路の受入も定義する。シナリオ・レベルデザイン・会話・フラグ管理を、プログラムスキルのない人が入力・編集できることを機能要件にする。

ゲーム画面と管理画面の画面一覧・表示状態を決めたら、[画像生成から画面実装へ](screen-design.md) に従ってデザイン画像を生成する。画像と機能仕様を揃えてから該当画面を実装する。

特に境界を決める: 観測と確定、定義と実行状態、章を始める処理とロードで復元する処理、表示と状態更新。イベントを反復・同時実行しても副作用が重複しないか、無効操作で部分的に状態が変わらないかを必要な範囲で定義する。

レビューは次の観点を対象機能に合わせて選ぶ。全編の反復レビューを着手条件にしない。

| 観点 | 主な問い |
|---|---|
| 整合性 | 共通表と個別データで日付・ID・数値・条件が一致するか |
| 実装ギャップ | シナリオが要求する機能に型・API・状態遷移があるか |
| プレイヤー体験 | 目的、操作、失敗理由、次に試せることが画面から分かるか |
| ゲームプレイ | 判断する余地があるか。必要な情報は判断前に取得できるか |
| 異常経路 | 順序変更、連打、再訪、資源枯渇、ロードで詰まらないか |
| 制作性 | 制作者が新しいコンテンツを作り、保存して実行できるか |

指摘を採用したら正本・個別データ・受入条件へ反映する。致命的な未決だけ先に解消し、他は必要になる段階まで保留する。

## 3. 段階と受入条件を分ける

段階名や数は調整してよい。各段階の終わりを観察可能な行動で定義する。

| 段階 | 作るもの | 次へ進む証拠 |
|---|---|---|
| 技術検証 | 最大の技術リスクを試す最小場面 | 対象環境で狙った現象が起きる。処理後の後始末も成立 |
| コアループ | 1課題、最小の操作と結果、管理画面でその課題のデータを編集、必要なら保存 | 試行→判断→行動→結果→次の試行が一周する |
| 機能統合 | 仮素材で開始から区切りまでつなぎ、管理画面で新規区間を制作 | 生成デザインを基準にしたUI、実データ、遷移、保存・再開、コード不要の制作経路が通過 |
| 品質見本 | 代表区間を製品に近い絵・音・操作感へ | 実プレイで読みやすさ・操作性・性能・制作費を確認 |
| 量産 | 検証した制作単位で範囲を拡張 | 新規データが共通検査を通り、前後の接続も通過 |
| 仕上げ・配布 | 最適化、入力機器、品質設定、移行、ビルド | 対象機器の配布物で主要経路が動作 |

MVPの長さやステージ数は検証したい体験と制作予算から決める。短いゲームなら複数段階を一つの実装単位にまとめてもよい。機能統合前の完成素材量産や、面白さの未検証を大量の仕様で埋める進め方を避ける。

## 4. 依存関係をタスクに落とす

各タスクに「仕様ID / 前提 / 対象ファイルまたは制作単位 / 受入条件 / 確認方法 / 状態」を付ける。状態の例は未着手・実装中・実装済み未検証・検証済み・阻害あり。

例えば「条件定義→条件評価→条件で変わる仕掛け→操作UI→区間の通過」と依存を並べる。共通型や状態モデルは利用側より先に定めるが、巨大な共通基盤を先に完成させない。早く一つの操作が画面に届く縦方向の実装を作る。

実装の一巡:

1. 受入条件と再現用の初期状態を決める。
2. 画面実装を含む場合はデザイン画像の生成と確認を先に完了し、必要なデータ・ランタイム・管理画面・ゲームUIを小さく接続する。
3. 変更した規則を適切なテスト層で確認し、実行して挙動を見る。
4. 失敗を仕様・コード・データ・アセット・入力・環境に切り分け、根本の編集元を修正する。
5. 関係する仕様、テスト、実行記録を揃え、次の受入へ進む。

## 5. 管理画面を仕様とともに実装する

コンテンツ一覧、シナリオ進行、レベル配置、会話、フラグ・条件・処理の管理を、仕様の段階から設計する。実装は各ゲーム機能と対応させて段階的に進め、対象コンテンツの量産前にその制作経路を完成させる。制作をコードやResourceの手編集だけで済ませて管理画面を後回しにしない。詳しい要件は [制作者向け管理画面](authoring-ui.md) を参照する。

ツールの成功条件はボタンやタブの数ではなく、制作者が「新しい小場面を作る→条件を設定→本編へ登録→保存→再読込→起動→意図通りの反応を確認」を完了できること。既存データの閲覧や、保存サービス単体の成功から制作全体の完了を推定しない。
