# 文書とデータの構造

## 最小構成から育てる

小規模な新規ゲームなら次で始める。既存の同等文書があれば再利用する。

```text
AGENTS.md                    作業入口。正本、規約、検証コマンドへの案内
docs/
  index.md                   ファイル、責務、仕様IDの対応表
  concept.md                 体験の仮説、コアループ、規模、非目標
  spec.md                    ゲームルール、管理画面、データと実装契約
  roadmap.md                 段階、依存関係、受入条件、現在の状態
  dev.md                     Godotの版、起動、テスト、データ・アセット運用
  manual.md                  非プログラマー向けの入力・編集・実行手順
```

ファイルを増やす契機は、別々に更新される責務ができたとき。長くなったから機械的に等分するのではなく、読む目的と変更のまとまりで分割する。初期は管理画面の仕様も `spec.md` に含め、編集項目や制作手順が増えたら独立させる。

## 大きくなった場合の構成例

```text
docs/
  index.md
  concept.md
  spec/
    01_overview.md            体験、操作、コアループ
    02_core_mechanics.md      判定・コスト・成功失敗
    03_world_and_progress.md  ステージ構成、進行、状態遷移
    04_ui_ux_audio.md         情報提示、フィードバック、アクセシビリティ
    05_runtime_contracts.md   データ、API、イベント順序、セーブ
    06_content_contracts.md   個別コンテンツの必須項目と共通表
    07_authoring_ui.md        非プログラマー向け管理画面・制作手順・受入
  design/                    画面一覧、生成画像への参照、状態・遷移、トークン
  scenarios/                 章・レベル・ミッションなど制作単位別
  dev/
    environment.md           版、導入、初回インポート、起動
    repository-layout.md     保存場所、命名、編集元、生成物
    conventions.md           コード・ID・入力・イベントの規約
    testing.md               テスト、実プレイ、配布ビルドの確認
    asset-pipeline.md        原稿、書き出し、配置、実機受入
    reports/                 実行環境・再現手順・結果と証拠
  review/                    指摘、判断、反映先、未対応
  manual/                    制作者向け管理画面の入力・編集・実行手順
  roadmap.md
CHANGELOG.md                 意味のある仕様・挙動の変更履歴
```

ファイル数と連番は例。章がないゲームでは `scenarios/` をレベル、ラウンド、カードセット等に置き換える。制作規模に合わせ、同じ責務を重複して説明するファイルは増やさない。

## 正本と参照

通常は共通仕様を個別シナリオより上位にし、アセット利用ガイドやレビューは共通仕様の変更を暗黙に行わない資料とする。既存プロジェクトに優先順位があれば従う。

- `docs/index.md` に「ファイル / 担当するルールまたは仕様ID / 概要」を置く。
- 参照が多いルールは `SYS-SAVE-001` 等の安定IDと見出しリンクを持つ。既存の `spec §N` を使うプロジェクトはその方式を維持する。分割時に参照先が消えないよう目次・リンクも更新する。
- 数式、タイムライン、コスト、章間引き継ぎ、解禁条件など横断値は共通表を正本にする。個別文書は参照し、実装に必要な差分だけ書く。
- `AGENTS.md` は入口として短く保つ。ロードマップの予定を現在の状態として転記しない。仕様と実装が違えば明示し、どちらを修正すべきか目的から決める。
- 未決事項には決定が必要な段階を付ける。実装契約に関わる未決と、後で変えられる名称・装飾を分ける。

## 記述テンプレート

必要な項目だけ使う。空欄を大量に作るための必須様式ではない。

### システム仕様

```markdown
## SYS-XXX: 機能名
プレイヤー体験・目的:
発火条件と入力:
参照する状態 / 更新する状態:
判定規則: 数値、単位、境界、複数成立時の順序
出力と画面・音の反応:
無効操作・失敗・取消・再試行時:
保存・ロード・再入場時:
依存する仕様IDとデータ:
制作者が管理画面で変更できる項目・入力制約・プレビュー:
受入例: 初期状態 → 操作 → 期待状態・表示
未決事項と決定期限:
```

「適切に」「必要に応じて」で実装判断が分かれる箇所は具体化する。内部状態が成立しても、プレイヤーに結果が分からない仕様は体験として不足している。

### 個別コンテンツ

```markdown
## LEVEL-XXX: 制作単位名
開始状態・入口 / 持ち込む状態:
プレイヤーの目的と知っている情報:
必須経路: 場所 → 操作 → 条件 → 状態変化 → 確認できる反応
任意・分岐経路 / 取り逃しの扱い:
終了条件 / 次へ渡す状態:
使用するID・データ・会話・アセットと定義元:
管理画面での作成・登録・編集手順:
予算: 消費資源、所要時間、必須操作数（必要なもののみ）
再訪・失敗・セーブ復帰:
QA: 通常経路、順序違い、反復、資源不足、復帰
```

必須項目を共通仕様に定義すると、章ごとの欠落を機械検査しやすい。物語の梗概と、実装できる進行表を区別する。

### レビュー記録

```markdown
対象リビジョン・観点:
| 指摘ID | 再現・根拠と影響 | 判断 | 反映先 | 検証 | 状態 |
```

状態は提案中・採用・却下・延期・反映済みなど。修正の指示と正本への反映を別に追跡する。古い指摘が現時点でも残るかは最新のコードと履歴で確認する。

## コード・コンテンツ・アセットの境界

```text
project.godot                   GodotプロジェクトとInput Map
.godot-version                  実行時に確認した最新安定版の記録
core/ と機能別ディレクトリ       型付きGDScriptによるランタイム実装
addons/content_editor/          制作者向け管理画面（EditorPlugin）
content/                        会話、ステージ、条件等の定義
levels/                         Godotのシーン・配置
art/ audio/ shaders/            製品が使う素材
assets/source/                  編集原稿、生成元、デザイントークン
assets/source/ui/designs/       画像生成で作った画面案、採用版、生成指示
tools/                          生成器、lint、検査、プレイ台本
tests/                          機能・統合・コンテンツの回帰テスト
build/ reports/                 再生成できる出力。原則非追跡
```

- 編集用原稿と実行用素材を分ける。原稿・巨大なプレビュー・開発用データを不要にインポートや配布へ含めない。
- IDは表示名と分離し、一意性・参照の正本を決める。差分と競合を扱いやすい制作単位でファイルを分ける。
- 管理画面は `content/` の型付きResourceと `levels/` のSceneを編集し、ゲームも同じ定義を読む。編集用に複製したデータだけを更新する構成にしない。管理画面専用のメタデータや開始プリセットは製品データと分離する。
- 固定の定義とプレイ中の可変状態を分離する。保存対象・スコープ・リセット契機を仕様化する。
- 生成物には生成元と再生成コマンドを明示する。エディターからも編集するなら、再生成による上書きを検知し、編集を生成元へ戻す運用か、生成を打ち切る運用を決める。確認記録だけを更新して変更を消さない。
- アセットは「制作済み / エンジン読込済み / 配置済み / 実プレイ受入済み」を分けて記録する。採用版、単位・軸、材質、衝突、ライセンス・入手元を必要に応じて利用ガイドへ残す。
- バイナリは規模と運用に応じてLFS等を使う。自作コードやテキストデータまで差分不能な設定にしない。
