# 画像生成からGodotの画面実装へ

## 必須の順序

ゲーム画面と制作者向け管理画面の新規作成・デザイン変更は、画面要件を整理→画像生成機能でデザインを生成→生成画像を確認・調整→Godotで実装→実画面で比較、の順に進める。文章だけのデザイン指示や、実装後のスクリーンショットを最初のデザイン生成の代わりにしない。

既存デザインを維持する挙動修正では画像を作り直さない。仕様だけの依頼では生成デザインと画面仕様までを成果物にし、ゲーム実装へ依頼を拡張しない。

## 1. 画面要件を整理する

画面ID、利用者、目的、表示サイズ・アスペクト比、入力機器、表示する実際の文言、主要操作、情報の優先順位、表示状態、隣接画面との遷移を定める。空・選択中・入力エラー・保存中・完了など、操作に必要な状態も仕様に含める。

管理画面では編集欄・検索・プレビュー・保存操作が成立する配置を先に決める。ゲーム画面では視界、読みやすさ、操作提示を優先し、背景や装飾で必要な情報を隠さない。

## 2. 画像生成機能で具体的なデザインを作る

利用可能な画像生成機能を実際に呼び出す。画像生成用skillが利用できる環境ではその手順を読む。機能が利用できない、または生成エラーの場合はエラーと未完了の画面を報告し、その画面の実装へ進まない。

生成指示には次を含める:

- 画面の用途、対象サイズ、ゲームの美術方針、色・書体の方向性。
- 各領域に必要な内容、実際の文言、ボタン・入力欄・一覧・選択状態。
- 視認性、余白、情報密度、コントラスト、操作可能な大きさ。
- 既存の採用デザインがある場合は参照画像として使い、共通部品を揃える。

各新規画面を覆うデザイン画像を作る。複数画面をまとめた画像でもよいが、実装に必要な配置と文字サイズを判断できる解像度にする。装飾的な雰囲気図だけで終わらせない。

生成画像を開いて実際に確認し、要件の欠落や読みづらい構成があれば再生成・編集する。ユーザーに見える形で提示し、採用する版を明確にする。ユーザーが承認を求めていない限り、ここに追加の承認待ちは設けない。

## 3. 画像を実装可能な画面仕様へ落とす

採用画像と生成指示を `assets/source/ui/designs/` 等へ保存し、画面仕様から参照する。画面ID、採用版、状態、表示サイズを対応付ける。

画像からレイアウト、余白、色、書体、ボタン寸法、アイコン、共通部品を整理してトークン化する。生成画像の文字崩れや、描かれただけで機能しない操作はそのまま再現せず、正しい文言と機能仕様へ整える。通常・フォーカス・押下・無効・エラー状態を補完する。

## 4. Godotで実装する

`Control`、`Container`、アンカー、サイズフラグ、`Theme`、フォント等を使い、採用画像を基準にレイアウトと共通部品を実装する。画像一枚を画面全面に貼るだけで入力欄やボタンを代用しない。背景・装飾・アイコン等は必要な部品として切り分け、文字と操作部品は実際に機能させる。

管理画面のフォームは型付きデータに接続し、保存・再読込・エラー表示を実装する。ゲーム画面は実際の状態・入力に接続する。ウィンドウサイズ変更、長い文字列、スクロール、キーボード操作でも意図した優先順位を保つ。

## 5. 生成デザインと実画面を比較する

採用デザインと同じサイズ・状態でGodotを起動し、実画面のスクリーンショットを取得する。主要領域の位置・余白・色・文字・部品の大きさを比較して修正する。仕様上の理由で変更した箇所は画面仕様へ反映する。

見た目の確認に加えて、入力・フォーカス・選択・遷移・編集・保存を実操作で確認する。生成画像、実装画面、確認した表示状態と操作、未確認のサイズ・状態をQA記録で区別する。
