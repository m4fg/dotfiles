# Game Dev Workflow

プレイヤーに起きる体験を出発点にし、仕様・データ・コード・実行結果を追跡できるGodotゲーム開発を進める。シナリオ等の制作は非プログラマーが管理画面で完了できるように設計し、ゲーム画面と管理画面は画像生成でデザインを作ってから実装する。

## 着手時

1. ユーザーの依頼範囲と既存の `AGENTS.md`、文書目次、起動方法、作業ツリーの変更を確認する。既存プロジェクトは現行の構成を優先する。
2. 現在地を「アイデア / 技術検証 / コアループ / 機能統合 / 品質見本 / 量産 / 仕上げ」から特定する。文書に書かれた計画と、コードや実行記録が示す実績を区別する。
3. 次に確認するプレイヤーの行動と、その成功条件を一つ選ぶ。ユーザーが仕様整理だけを求めている場合は、その範囲の成果物を作り、実装へ勝手に拡張しない。
4. エンジンはGodotとし、skill実行時に公式サイトで最新の安定版を確認して使用する。具体的な版番号をこのskillに固定しない。対象機器・操作・規模の未決事項のうち、今の判断を妨げるものだけ確認する。他は仮定または `[[TBD: 内容 / 決める段階]]` として扱う。

## 必要な参照を選ぶ

| 今回の作業 | 読む資料 | 得るもの |

| 仕様書、シナリオ、リポジトリの構成 | [文書とデータの構造](references/document-structure.md) | 正本・参照規約、最小構成、再利用用テンプレート |
| 実行、デバッグ、QA、制作ツールの受入 | [実行と検証](references/runtime-verification.md) | 再現手順、検証層の選択、証拠付き結果 |
| 仕様作成、シナリオ・レベル・会話・フラグの編集 | [制作者向け管理画面](references/authoring-ui.md) | コード不要の制作機能、保存契約、制作経路の受入 |

新規立ち上げ・仕様作成では開発の進め方、文書構造、制作者向け管理画面を読む。画面を設計するときは画像生成から画面実装への資料を読み、実装前に実行と検証も読む。

## 一貫して守ること

- **仕様の正本は一つ。** 共通ルール、個別コンテンツ、運用手順、検証記録の役割を分け、数値や条件の重複定義を避ける。変更時は関係する参照・データ・実装・受入条件を同じ変更単位で揃える。
- **段階を小さくする。** 最も不確かな技術とコアループを先に動かす。機能がつながることと、完成品質の素材・演出が揃うことは別の受入にする。全章・全ステージ・全制作ツールの先行整備を標準にしない。
- **入力から結果まで通す。** 状態を直接書き換えるテストと、製品の入力経路で成功するテストを区別する。制作ツールは新規作成→編集→保存→再読込→ゲーム内反映まで検証する。
- **結果の限界を残す。** 文書lint、単体テスト、起動、通しプレイ、初見の理解、製品ビルドを別々に報告する。未実行を成功に含めない。
- **制作を管理画面で完結させる。** 仕様作成時からシナリオ、レベル配置、会話、フラグ・条件・処理の編集画面を必須成果物に含める。コードやデータファイルの手編集を通常の制作手順にしない。
- **デザイン画像を先に作る。** 新規画面やデザイン変更は画像生成機能で具体的な画面案を生成・確認し、その画像を基準にGodotで実装する。ゲーム画面と管理画面の両方に適用する。
- **環境制約を尊重する。** 指定ツールや取得元でエラーになったら原因と未確認範囲を記録する。代替禁止の指示がある環境では別経路へ切り替えない。

## 作業を閉じるとき

依頼に応じて文書・コード・検証記録を実際に作成または更新し、リンクを渡す。現在達成した体験、実行した確認、未確認事項、次の受入条件を短く示す。未反映の提案を採用済み仕様として扱わない。
