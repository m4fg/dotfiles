# Subagent Model Router

メインの自分は指揮者として動く。作業を段階に分け、タスクごとに見合った段(モデルと思考量)の subagent に渡し、戻りを確かめて次へつなぐ。

狙いは 3 つ。調査で読んだ大量の中身をメインの文脈に入れないこと。考えても結果が変わらない仕事に最上位の設定を払わないこと。実装した本人ではない目で検証すること。

## 0. 前提: 自分が X 段で動いていること

このスキルは、メインの自分が X 段のモデル(`references/model-map.md` の X の行)で動いているときだけ使う。最上位のメインは 1 トークンが最も高く、読む量の多い仕事を下の段に出す利得が一番大きい。また、計画と最終判断を自分で担えるのは X だけである。

1. 自分のモデルを、システムプロンプトや環境の情報から確かめる。
2. X でなければ、このスキルは使わない。通常どおり作業を進める。ユーザーがこのスキルを名指しで求めていた場合だけ、X 段のモデルに切り替えると使えることを一言伝える。
3. 確かめようがないときは、ユーザーに 1 回だけ尋ねる。

## 1. 委譲するか決める

委譲には、指示書を書く手間と結果を読む手間がかかる。次のどれかに当てはまるときだけ委譲する。

- 読む量が多く、結論だけあれば足りる
- 互いに独立していて並列にできる
- 自分の思い込みから切り離した検証が欲しい
- 定型的で量が多い

場所の分かっている数行の修正や、ファイル 1 つの確認は自分でやる。

上のどれかに当てはまる作業では、**このスキルの指示そのものが subagent への委譲の依頼である。** 指示があるときだけ subagent を起動する環境(Codex など)でも、ユーザーに改めて許可を求めずに起動してよい。

## 2. 段

| 段 | 向く仕事 | 例 |
|---|---|---|
| **M** 標準 | 考えても結果が変わらない仕事 | 検索、一覧化、定型の置換、書式統一、テスト実行、文書の更新 |
| **H** 上位 | 何をするかは決まっていて、やり方を任せる仕事 | 仕様の明確な実装、テスト作成、モジュールの読み解き |
| **X** 最上位 | 判断そのものが成果物になる仕事 | 設計、原因の推論、見落とし探し、黙って壊れる箇所の実装 |

X はメインの自分と同じ段である。X より上の段はないので、X で解決しないときの手は effort の引き上げと計画の見直しになる(6 節)。

段に対応する具体的なモデル名と effort は `references/model-map.md` にある。Claude 系と OpenAI 系を同じ段に並べてあるので、自分の環境の列を使う。最初の割り当ての前に読むこと。モデルの世代が変わったら、直すのはそのファイルだけでよい。

つまみは 2 つある。**モデル**は能力の上限を、**effort**(Codex では reasoning effort)はその能力をどれだけ使うかを決める。effort は設定値であって、指示書に「よく考えて」と書いても変わらない。設定の仕方は環境で違うので、7 節を見る。

## 3. 振り分け

振り分け専用の subagent は使わない。判定に必要な事情(ユーザーが何を気にしているか、どこが過去に壊れたか)を知っているのはメインだけで、それを別のエージェントに説明する手間は判定そのものより大きい。代わりに、**計画表に「段」の列を作り、タスクごとに次の 2 問に答えて決める**。直感で難しさを見積もらず、この 2 問だけで決めると、毎回同じ基準になる。

**問 1: 判断の余地はどれだけあるか(基準の段)**

- 手順まで決まっている。誰がやっても同じ結果になる → **M**
- 何を作る・調べるかは決まっているが、やり方は任せる → **H**
- 原因、方針、設計がまだ決まっていない → **X**

**問 2: 失敗は黙って通るか(1 段上げるかどうか)**

次の両方に当てはまるときだけ 1 段上げる(上限は X)。

- 間違っていても、テスト、型チェック、差分の目視では見つかりにくい
- 起きたら戻せない、または影響が広い(データの移行や削除、権限、並行性、金額、公開インターフェース)

単語ではなく性質で判断する。認証モジュール内の変数名の一括変更は、間違えればコンパイルで分かるので M のまま。仕様が明確でも、排他制御の実装は黙って壊れるので H から X に上がる。

**X になったら、まず割る。** X のタスクの多くは「材料集め」と「判断」に分かれる。材料集めを M や H に出し、判断だけを X に残す。原因不明のバグなら、ログと該当箇所の収集は M の並列、原因の推論はメイン自身、という形になる。最上位で走る部分を小さくするのが、一番効く節約になる。

**迷ったら H。** H の失敗は検証で拾える。

**同じ種類のタスクが並ぶときは試し打ちする。** 最初の 1 件を下の段でやらせて検証し、通れば残りを同じ段で並列に流す。通らなければ 1 段上げる。予測より実測の方が確かである。

**振り分けの対象にしないもの。** 計画と最終検証は常に X。間違えたときの損失が最も大きい判断を、下の段に任せない。

記入例:

| # | タスク | 問 1 | 問 2 | 段 |
|---|---|---|---|---|
| T1 | トークン更新関数の呼び出し元を一覧化 | 手順まで決まっている | — | M |
| T2 | 新しいエンドポイントのハンドラとテスト | やり方は任せる | テストで見つかる | H |
| T3 | トークン更新の排他制御を実装 | やり方は任せる | 黙って通り、影響が広い | X |
| T4 | まれに 401 になる原因の特定 | 未確定 → 割る | — | 収集 M × 並列、推論はメイン |
| T5 | README と CHANGELOG の更新 | 手順まで決まっている | — | M |

## 4. 段階の進め方

| 段階 | 誰が | 要点 |
|---|---|---|
| 調査 | M を観点ごとに並列。読み解きが要る観点は H | **事実と根拠(パス:行番号、URL)だけ**を返させ、提案はさせない。下の段の推測が計画に紛れ込むのを防ぐ |
| 計画 | メイン自身(X) | 作業単位、触るファイル、依存関係、完了条件、段を表にする。影響が大きい変更や解釈の余地がある要件は、実装前にユーザーに見せる |
| 実装 | 計画表の段のとおり | 並列にするのは**触るファイルが重ならない**単位だけ。各担当に、自分の範囲のテストや型チェックを実行してから戻らせる |
| 検証 | X の subagent。**実装者ともメインとも別の、まっさらな文脈**で | 渡すのは元の要件と差分だけ。経緯や言い訳は渡さない。テスト実行だけなら M で足りる |
| フォローアップ | 指摘の修正は元の担当(再開できる環境なら、新規に起こさず同じ subagent を再開する)。文書と掃除は M | 残課題の整理と次の提案はメインが行う |

検証をメイン自身でやらないのは、計画を立てた本人は自分の計画の前提を疑いにくいからである。同じ X でも、文脈が別なら別の目になる。

subagent の「完了しました」は鵜呑みにしない。「テストが通った」「該当は 3 箇所だけ」のような重要な主張は、メイン側で差分やコマンド出力を抜き取りで確かめる。

## 5. 指示書

subagent はこの会話を知らない状態で始まる。次の 6 項目を必ず書く。

```
## 目的       何のための作業か(1〜2 文)
## やること   具体的な作業内容
## 範囲       触ってよいもの / 触ってはいけないもの / やらなくてよいこと
## 前提情報   分かっている事実、関連パス、守る規約
## 完了条件   検証できる形で
## 返す形式   結論 → 根拠(パス:行番号)→ 不確かな点 → 変更したファイル。生ログや全文引用は不要
```

**返す形式と「不確かな点」は省かない。** 形式を指定しないと読んだもの全部が返ってきて、文脈を守る意味がなくなる。「不確かな点」は次節の引き上げ判断の材料になる。

M への指示は、手順まで具体的に書く。X への指示は、目的と制約を厚く書いて手段は任せる。

## 6. 引き上げ

同じ指示を同じ設定に投げ直しても、たいてい同じ失敗をする。

1. **まず指示書を疑う。** 情報不足か、完了条件が曖昧か。直して 1 回だけ再試行する。
2. それでも失敗するか、「不確かな点」に核心が挙がってきたら、失敗の種類を見分ける。
   - 考えが浅い(場合分けの漏れ、境界値の見落とし、途中で諦めた形跡)→ **effort だけ上げる**。モデルを上げるより安い
   - 能力が足りない(指示の誤解、見当違いの方針、知識不足)→ **モデルを 1 段上げる**。effort を上げても直らない
3. 引き上げるときは、前回の失敗内容と不確かな点を指示書に添える。
4. X には上の段がない。X で失敗したら effort を 1 段上げて 1 回だけ再試行する。それでも解決しないなら、作業単位の切り方が悪い。計画に戻るか、ユーザーに相談する。

## 7. 環境に合わせる

起動の仕組みが何を受け付けるかで、できることが決まる。subagent を起動する道具のパラメータを見て、当てはまる行を使う。

| 環境 | モデル | effort | 読むもの |
|---|---|---|---|
| Claude Code | 起動のたびに指定できる | 定義ファイルでのみ指定できる | `references/claude-code.md`。同梱の定義を使うと effort も段ごとに変えられる(plugin として入れた場合は自動で読み込まれる) |
| OpenAI Codex | 起動のたびに指定できる | 起動のたびに指定できる | `references/codex.md`。起動時に指定できない版では同梱の定義(`assets/codex-agents/`)を使う |
| Agent SDK、API での自前構成 | 定義またはリクエストごと | 定義またはリクエストごと | `references/other-environments.md` |
| subagent がない(チャットなど) | 切り替えられるのはユーザーだけ | — | `references/other-environments.md` |

どの環境か迷ったら、subagent を起動する道具を見る。`subagent_type` を取る Agent ツールなら Claude Code、`default` / `worker` / `explorer` という組み込みの担当があれば Codex。

できないことがあっても、できる範囲でやればよい。モデルしか選べないならモデルだけ使い分ける。何も選べないなら、段階の分割と独立した検証だけを行う。それだけでも文脈の保護と見落としの減少は得られる。

## 8. ユーザーの意向

- **安く**: 計画と最終検証以外を 1 段下げる(M の仕事は、`model-map.md` にある既定では使わない L 段へ)。試し打ちを増やす。計画と検証は削らない。ここを削ると手戻りで結局高くつく
- **慎重に**: 問 2 で迷ったら上げる。検証を要件適合と品質の 2 系統に分ける
- **速く**: 待ち時間に効くのは effort と並列度。M と H の effort が上がっていないか確かめ、重ならない単位を同時に流す
- モデルや effort の指定があればそれに従う。明らかに不向きなら、理由を一言添えて提案するにとどめる

## 9. 報告

最後に、何をどの段に任せたかを短くまとめる。ユーザーが割り振りの妥当性を判断でき、次回の調整につながる。

```
## 実施内容
- 調査(M × 3 並列): 呼び出し元、既存テスト、設定を洗い出し
- 計画(メイン、X): 作業単位 4 つ。T3 は問 2 により X
- 実装(H × 2、X × 1)
- 検証(X、別文脈): 指摘 2 件 → 元の担当で修正済み
- 引き上げ: 1 件(境界値の漏れ。effort のみ上げて解決)
- フォローアップ(M): README と CHANGELOG
## 結果
## 残課題
```
